## 2026-09-08 — fatia 30: Esqueci minha senha (redefinição via Supabase)

Fluxo de redefinição de senha para coach e alunos. No login, um link **"Esqueci minha senha"** leva a `/esqueci-senha` (pede o e-mail) → o app dispara o `recover` do Supabase, que **envia** um e-mail com um link de redefinição → o link abre `/redefinir-senha`, onde a pessoa define a senha nova. Respostas **genéricas** ("Se houver uma conta com esse e-mail, enviamos um link") para não revelar se o e-mail existe; senha nunca gravada nem logada (só trafega form→servidor→Supabase); as duas rotas são públicas no gate. O token de recuperação chega no fragmento da URL (`#access_token=...`) e um JS mínimo na página de redefinição o lê para um campo escondido — sem token, mostra "link inválido/expirado". Integração isolada em `auth/supabase.py` (`recover` + `atualizar_senha`, com `AuthTokenInvalido` para link expirado). Sem migração. Testes novos (`tests/test_reset_senha.py`, 18 casos: gate, link/aviso no login, anti-enumeração, validação de senha, token vazio/expirado, sucesso, + unit das chamadas ao Supabase); suíte com **709 verdes**. **Pré-requisito para o envio real funcionar** (ação do PO, guiada): ligar um provedor de e-mail (Resend) no Supabase (Custom SMTP) e liberar a Redirect URL `.../redefinir-senha`.

## 2026-09-08 — correção: signup do Supabase com "Confirmar e-mail" ligado

Bug pego numa ativação real: ao criar o acesso, o app mostrava "Não foi possível criar o acesso agora" mesmo com o Supabase respondendo 200. Causa: o `auth/supabase.py::signup` só lia o usuário aninhado em `data["user"]`, mas o endpoint `/auth/v1/signup` do GoTrue devolve os campos do usuário **no topo da resposta** (sem `access_token`) quando o projeto está com **"Confirm email" ligado** — então o app achava que "não veio user.id". Agora aceita os dois formatos (usuário aninhado com sessão *e* no topo sem sessão) e, de quebra, trata o caso de e-mail já registrado (resposta ofuscada do GoTrue com `identities` vazio → "e-mail já tem conta"). Testes unitários novos do parsing das duas formas (`tests/test_supabase_signup.py`); suíte com **691 verdes**.

## 2026-09-07 — fatia 29: Link de ativação — o aluno cria o próprio acesso

O coach deixou de precisar criar o usuário do aluno na mão no painel do Supabase. Agora, na ficha do aluno (quando ele tem e-mail e ainda não tem acesso), aparece um **link de ativação** pronto pra copiar; o coach **envia esse link** ao aluno (WhatsApp, etc.). O aluno abre o link e cai numa página **"Crie seu acesso"**: vê o e-mail dele (travado) e **define a própria senha** — a conta é criada no Supabase na hora e ele já entra na sua área. **Segurança:** a senha é digitada pelo próprio aluno e vai direto ao Supabase (mesmo padrão do login); o app **nunca** grava nem registra a senha, e ninguém — nem o coach — a vê. O link é um **token assinado com validade de 7 dias** (usa o `itsdangerous` que já temos), amarrado a um aluno; se o aluno já ativou, o link não cria conta dupla (manda pro login); um link sem e-mail na ficha é tratado como inválido. **Sem segredo novo, sem servidor de e-mail** (o coach entrega o link; usa o `anon key` do Supabase). Camadas: integração (`auth/supabase.py::signup`, que distingue "e-mail já registrado"), token assinado (`auth/tokens.py`), rotas públicas `GET/POST /ativar/{token}` + o link na ficha, e a página `auth/ativar.html` (estados: criar acesso / link inválido / já ativado / e-mail já existe / confirme o e-mail). Sem migração. Testes novos (`tests/test_ativacao_aluno.py`, 17 casos: token, todos os estados, senha curta/divergente, e-mail já registrado, link só aparece na ficha quando elegível); suíte com **688 verdes**. Verificado ao vivo (a página renderiza; link sem e-mail dá "inválido"). **Config do Supabase que fica com o PO:** ligar "Allow new users to sign up" e, de preferência, desligar "Confirm email" (o link do coach já é a verificação) para a ativação ser instantânea — se ficar ligado, o fluxo degrada para "confirme o e-mail e depois entre".

## 2026-09-03 — fatia 23: Login (Fase 1 do épico de autenticação) — Supabase Auth + sessão do coach

Primeira fase da autenticação: o painel passa a exigir login; clicar em "Entrar" (vitrine) leva à tela de login. **Abordagem:** o Supabase Auth só **confere a senha no login** (`POST /auth/v1/token`); depois o app mantém a **própria sessão assinada** (cookie via `SessionMiddleware`), sem precisar verificar JWT a cada requisição nem do JWT secret.
